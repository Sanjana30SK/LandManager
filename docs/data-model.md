# Data Model

Database: **MongoDB**, accessed through **Mongoose**.
Collection: `parcels` (Mongoose model `Parcel`).

## Parcel document

| Field         | Type                    | Required | Rules / default                                                  |
|---------------|-------------------------|----------|------------------------------------------------------------------|
| `_id`         | ObjectId                | auto     | Generated by MongoDB. Exposed to clients as `id`.                |
| `title`       | String                  | yes      | Trimmed, 3–100 characters. Used for search.                      |
| `description` | String                  | no       | Up to 1000 characters. Default `""`.                             |
| `ownerName`   | String                  | no       | Up to 100 characters. Dummy data only.                           |
| `areaSqm`     | Number                  | no       | Greater than 0. Area in square metres.                           |
| `status`      | String (enum)           | yes      | One of `STATUSES` below. Default `available`.                    |
| `landUse`     | String (enum)           | yes      | One of `LAND_USES` below.                                        |
| `location`    | GeoJSON `Point`         | yes      | `{ type: "Point", coordinates: [lng, lat] }`                     |
| `boundary`    | GeoJSON `Polygon`       | no       | Reserved for a future parcel outline. Not used by the app yet.  |
| `createdAt`   | Date                    | auto     | Added by Mongoose `timestamps: true`.                            |
| `updatedAt`   | Date                    | auto     | Added by Mongoose `timestamps: true`.                            |

### Allowed values

```
STATUSES  = available | sold | reserved | under_dispute
LAND_USES = residential | commercial | agricultural | industrial | institutional
```

These lists live in one file (`server/src/constants/parcel.js`) so the schema,
the validator and the seed script all use the same values.

## Example document (as stored in MongoDB)

```json
{
  "_id": "6735a1f2c9e77b0012ab34cd",
  "title": "Plot 42, Whitefield",
  "description": "Corner plot near the metro station",
  "ownerName": "Ravi Kumar",
  "areaSqm": 1200,
  "status": "available",
  "landUse": "residential",
  "location": { "type": "Point", "coordinates": [77.7499, 12.9698] },
  "createdAt": "2026-11-13T10:00:00.000Z",
  "updatedAt": "2026-11-13T10:00:00.000Z"
}
```

## Indexes

| Index                  | Why                                                                 |
|------------------------|---------------------------------------------------------------------|
| `location: "2dsphere"` | Lets MongoDB understand the point as geography (enables geo queries later). |
| `{ status: 1, landUse: 1 }` | Speeds up the bonus filters.                                   |
| `{ createdAt: -1 }`    | Lists the newest parcels first.                                     |

Search uses a case-insensitive regular expression on `title` (partial match,
e.g. `whit` finds "Plot 42, Whitefield"). A MongoDB text index was **not**
chosen because it only matches whole words.

## Key design decisions

1. **GeoJSON for location.** It's the format MongoDB's geo features understand,
   and Leaflet can read GeoJSON directly. Storing plain `lat`/`lng` numbers
   would block geo queries and the polygon bonus.
2. **Longitude comes first in GeoJSON** (`[lng, lat]`), while Leaflet uses
   `[lat, lng]`. To keep this bug away from the frontend, the API converts the
   point to `{ lat, lng }` in exactly one place (see `api-spec.md`).
3. **camelCase field names** (`ownerName`, `landUse`) because that's the
   JavaScript and MongoDB convention.
4. **Polygon area** (not built yet) would be calculated on the server with
   a library such as `@turf/area`, because MongoDB has no built-in area function.
